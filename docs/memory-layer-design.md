## 一、记忆是六件事，RAG 只是其中一件

把"记忆系统"当成"RAG"是最常见的误判。拆开看是六个能力，各有各的机制：

| | 能力 | 回答什么问题 | 机制 | 现状 |
|---|---|---|---|---|
| 1 | **找得到** | "上次关于中试基地是怎么说的" | 混合检索 + 层级切片 | RAG，已建大半 |
| 2 | **算得出** | "报市稿改到第几版了" | **从日志聚合**，不是检索 | `work_ledger` 有雏形，未接入对话 |
| 3 | **记得住** | "我说过周三前提交" | 逐轮抽取 + 调和 | `facts.py` 有骨架，缺抽取器 |
| 4 | **想得起** | 不用问就提醒你 | 常驻层 + 到期观察者 | 观察者层已有，未接记忆 |
| 5 | **忘得掉** | 做完的事别再占地方 | 生命周期与失效 | 只有设计 |
| 6 | **信得过** | "这条是哪来的" | 出处 + 置信度 + 用户优先 | 只有设计 |

**第 2 条最容易被 RAG 冒充。** "第几版"是聚合查询：就算把十个相关片段都召回，模型还得自己数，
且极易数错。这类问题必须走台账，不能走检索。

**第 4 条是"越用越好用"那种感觉的唯一来源**，也最难。

## 二、上下文工程：三条通道，预算分开

记忆层的核心问题不是"存什么"，而是**每一轮谁占了上下文预算**。三条通道互不挪用：

```
L0 常驻    每轮无条件付费     ≤ 800 token     未到期承诺 + 偏好 + 设置
L1 召回    模型主动要才付     ≤ 3000 token    混合检索（可展开）
L2 旁路    永不进上下文       0 token         ASR 热词、别名归并、检索文本注入
```

### L0 常驻：只放数量天然就少的

- 未到期 `commitment`（上限 10 条，按 due_at 就近截断）
- 全部 `preference` + `setting`（本来就没几条）

不放实体、不放历史、不放材料。它们要么进 L1，要么进 L2。

### L1 召回：做成工具，不做预处理

**每轮自动检索 = 每轮无条件付费，而大多数轮次根本用不上。**
做成工具让模型自己判断——和技能懒加载、和 Pi 的 "read the skill file when it matches" 是同一个道理。

现有实现已经是工具（`register_history_recall_tool`），这条做对了。

### L2 旁路：不进上下文的消费者

同一份实体投影，有三个消费者，其中两个不占一个 token：

- **ASR 热词**：投影成专名表喂给转录引擎
- **别名归并**：注意力层判断"零次方"和"燃气方"是不是一回事
- **检索文本注入**：把"燃气方 → 零次方"这条纠正注入到相关片段的**检索文本**里，
  让它可被找到，但**不出现在返回给模型的正文里**
  （对应 V5_dev 的 `caption_aux`：召回专用字段）

## 三、写入侧（记）

### 3.1 三个来源，经济性完全不同

绝大多数专名是智能体**读**出来的，不是用户**说**出来的。

| 来源 | 从哪来 | 例子 | 怎么处理 |
|---|---|---|---|
| `user` 用户说的 | user / assistant 消息 | "是零次方不是燃气方" | 逐轮闸门 → 抽取 |
| `observed` 智能体读到的 | 工具结果：ASR 转录、docx 正文、网页 | 转录里的"工信张传涛局长" | **入档时抽一次**，不逐轮 |
| `derived` 智能体做过的 | 工具调用本身 | 写了报市稿第 6 版 | **纯规则投影，零模型调用** |

- `user` 短、频繁 → 逐轮跑，靠闸门筛
- `observed` 长（一份转录几万字）、频次低 → 按文档抽一次，内容哈希去重
- `derived` 完全确定 → `build_work_ledger` 已经在干

**优先级：`user` 说的压过 `observed` 读到的。** ASR 把名字听错记下了，你后来纠正，永远听你的。
`observed` 出来的事实 confidence ≤ 0.7；其中的承诺类（"工信请我们牵头写材料"）标为**待确认**，
主动问一句再入库——否则你哪天打开待办，全是自己没答应过的事。

### 3.2 三级漏斗（user 通道）

```
每轮对话结束
   ├─[1] 闸门（纯规则，零成本）──► 实测 9 轮只有 3 轮过闸
   ├─[2] 抽取（一次小模型调用）── 结构化输出，一次返回所有槽位
   └─[3] 调和（纯规则，零成本）── ADD / UPDATE / NOOP，落成 memory/fact 事件
```

闸门放行信号：时间词、承诺动词、纠正词、周期性词。宁可多放——
假阳性只花一次小模型调用，假阴性丢一条事实。

跳过的形态：纯查询、纯 ASR 任务、纯执行（改文件跑测试，没产生新约定）。

### 3.3 槽位

| kind | 记什么 | 谁消费 |
|---|---|---|
| `commitment` | 承诺、待办、提醒 | L0 常驻 + 到期观察者 |
| `entity` | 正名与别名 | L2 旁路（热词 / 归并 / 检索注入）|
| `preference` | 口吻、格式、工作习惯 | L0 常驻 |
| `decision` | 定下来的事 | L1 召回 |
| `setting` | 长期默认值 | L0 常驻 |

**硬约束：每轮 ≤ 5 条候选，confidence < 0.5 丢弃。** 超了说明模型在凑数。

### 3.4 量控主力是调和，不是闸门

同一件事说十遍，库里还是一条：新东西 ADD，改口径 UPDATE（**覆盖，不是新增**），重复 NOOP。

生命周期：`commitment` 完成或到期即归档，不再进 L0；`entity` 长期有效；
`preference`/`setting` 被同 subject 新事实覆盖；`decision` 长期保留但只在 L1 出现。

## 四、读取侧（回忆）

### 4.1 语料

全部要进：

- **文件库**：现有材料，以及之后发进来的 pdf / word / 表格
- **完整聊天记录**：所有会话
- **会议转写**：ASR 产物
- 工作台账**不进检索**——它是聚合源，见第 1 节第 2 条

### 4.2 层级切片：只索引叶子，靠展开补语境

每类语料的树不同，但都是树：

| 语料 | 层级 |
|---|---|
| Word / PDF / Markdown | 文件 → 一级标题 → 二级标题 → 段落组 → **段落（叶子）** |
| 表格 xlsx / csv | 文件 → sheet → 表区 → 行组 → **行（叶子）** |
| 聊天记录 | 会话 → episode → 轮 → **消息块（叶子）** |
| 会议转写 | 会议 → 议题段 → **发言块（叶子）** |

规则：

1. **只索引叶子**，但叶子的检索文本里带祖先路径（V5_dev 的 `heading_path` 做法）。
   命中精度在叶子，语境完整性靠展开。
2. **表格每一层都必须继承表头。** 一行数据脱离表头没有意义。
3. **节点 ID 用内容哈希 + 路径**（文件 + 标题路径 + 序号），不能用行号或自增 id——
   否则重建一次索引，上一轮给模型的 id 全失效。
4. 聊天的树不天然存在，得造。`recall_archive.py` 的 `group_turns_into_episodes` /
   `should_merge_boundary` 已经在做这件事。

### 4.3 返回叶子 + 一张标好价的展开地图

**这是整个读取侧最关键的一处设计。** 决定"够不够"的只有模型自己，
所以把选择权交给它——但必须同时把账本交给它，否则它只能瞎开。

```json
{
  "id": "doc:报市稿#3.2/p4",
  "text": "……命中的最小片段……",
  "path": ["关于我市具身智能产业发展的思考和建议", "三、建议", "（二）建设中试基地"],
  "summary": "建议依托现有厂房建设具身智能中试基地，解决样机验证场地不足。",
  "expand": {
    "up1":  { "id": "doc:报市稿#3.2", "tokens": 420 },
    "up2":  { "id": "doc:报市稿#3",   "tokens": 1600 },
    "file": { "id": "doc:报市稿",     "tokens": 8200 }
  },
  "neighbors": { "prev": "…#3.2/p3", "next": "…#3.2/p5" }
}
```

看到 `up1` 才 420 token，模型会毫不犹豫地开；看到 `file` 是 8200，它会先试 `up1`。

展开工具两个入口：

```
recall_expand(id, scope="up1"|"up2"|"file"|"neighbors")
recall_expand(id, max_tokens=1500)      # 系统挑预算内最大的完整单元
```

约束：

- **展开有硬上限。** 超限时降级为"目录 + 各节 summary"，让模型再选一次。
- **展开时不切碎父节点**（切了反而读不通），照常返回完整父节点，
  但标一句"其中 p4 你已在上文见过"。它在缓存前缀里，重复代价很小。
- **同一轮内重复召回同一节点**，第二次只回"已在上文第 N 条"。

### 4.4 检索管线

```
query
  ├─ 元数据过滤（时间 / 项目 / 实体 / 账户隔离）  ← 先于语义，别让向量猜结构化条件
  ├─ BM25（jieba 分词）           top 20 ┐
  └─ dense（bge-m3）              top 20 ┘
                    ↓ RRF 融合（k=60，不依赖分数同尺度）
                    ↓ cross-encoder 精排（bge-reranker-v2-m3）
                    ↓ 叶子 top_k = 6，按 path 去重
```

**排序必须含时间维度。** 见 4.5。

### 4.5 从 V5_dev 抄什么、不抄什么

V5_dev 的检索是实战检验过的（研点赛全国第一），但它服务的是**静态手册**。

**该抄的三条：**

1. **检索文本 ≠ 精排文本 ≠ 返回文本。** 同一个 chunk 三套文本：
   - 检索：product + heading + summary + text + `caption_aux` + 别名（宁滥勿缺）
   - 精排：把关键字段提前，整体截到 900 字（迁就 reranker 长度上限）
   - 返回：父节点正文
   `caption_aux` 是**召回专用字段**——这正是我们注入别名的位置。
2. **summary 是 LLM 离线生成的，目的是"只看这一句就能判断要不要打开本节"。**
   他们踩过坑：早期 summary 是正文前 120 字截断，11% 以警告套话开头、信息量为零，
   导致模型选不准该读哪节。我们的展开地图靠的就是这个 summary。
3. **双 query 精排**：模型抽的关键词 rerank 取 6 + 用户原话 rerank 取 4，去重合并。
   两者命中的东西不一样，都要。

**不该抄的三条：**

1. **没有时间维度。** `retrieval_engine.py` 里一处 recency / 时间衰减排序都没有——
   手册是静态的，不需要。而记忆检索里"上次""上周""最新一版"是最高频意图。
   **这是最大的缺口，必须进排序公式，不是调参能补的。**
2. **手册 chunk 自足，聊天 chunk 不自足。** 手册一节讲完一件事；
   聊天里全是"那个文件""他说""按之前的口径"。所以聊天的父节点必须是完整的一轮或
   episode，单独捞一个消息块给模型**很可能误导**。
3. **静态索引 vs 只追加语料。** 手册可以整体重建索引；记忆语料每天在长，
   索引必须增量，且必须能从原始日志和文件完全重建（是投影，不是第二数据源）。

## 五、token 经济账

多一轮 ReAct 的真实成本：

| 项 | 量级 |
|---|---|
| 重发上下文 | 有 prompt cache，约 10% 价格，不致命 |
| **新一轮 reasoning token** | **大头**。output 比 input 贵数倍 |
| 延迟 | 多一次往返 |

推论：

1. **召回结果落在上下文末尾**，前缀不变，后续每步都是缓存命中。
   所以"单轮多给一点"比直觉上更划算——**倾向少轮次**。
2. **但展开要靠模型判断，所以轮次省不掉**——这正是层级切片的价值：
   它让"多的那一轮"发生得**少而准**，而不是取消它。
3. 控制展开率的两个手段：叶子切得够准（命中就够用）、
   叶子带 path 和 summary（不够用时一眼看出往哪开）。
4. **目标：八成问题一轮解决，两成展开一次。**
   若实测展开率过半，说明叶子切太碎，该调粒度而不是加轮次。

## 六、现状与缺口

现有 `history_recall.py` 已有：FTS5/BM25、MLX bge-m3 向量、RRF 融合、
父子分块（命中子块返回父段）、scope 隔离（current / project / account）、已注册为工具。

缺口：

| 缺口 | 说明 |
|---|---|
| **语料只有聊天记录** | 材料文件、会议转写全不在索引里 |
| **没有 rerank** | 只有 RRF。cross-encoder 精排是召回质量的大头 |
| **没有时间维度** | 见 4.5 |
| **返回父段全文** | 5 条 × 上限 240 单位一次灌下来，没有分级、没有展开地图 |
| **向量默认关闭** | `WORK_AGENT_HISTORY_RAG_ENABLED` 默认 `0`，现在跑的是纯 BM25 |
| **读旧 session_store** | 不是事件日志。两个数据源迟早不一致 |

## 八、为什么事实和索引都落在会话日志上

事实是 `memory/fact` 事件，追加进同一条会话日志，和"用户发消息""助手调工具"同一个流。
索引是这条日志加文件库的**投影**，随时可删可重建。

- 每条事实能追溯到产生它的那一轮
- 重放日志能复现整个记忆库
- 没有第二个数据源要维护、同步、担心不一致

和 `build_work_ledger` 从日志投出 49 个产物是同一个机制。

**自检判据**：把 `web_server.py` 里手写的 `ATTENTION_ALIAS_GROUPS` 整段删掉，别名归并仍然工作。
那 5 组本来就在历史对话里说过，真从日志读就一定读得到。删了就不工作，说明还在吃硬编码。
