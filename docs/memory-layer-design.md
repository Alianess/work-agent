## 〇、一句话

记忆层要回答的不是"存什么"，而是**每一轮谁占了上下文预算，以及凭什么**。

## 一、先分清四件事，别混成"记忆"

| | 问题长什么样 | 归谁管 | 状态 |
|---|---|---|---|
| **找得到** | "上次中试基地那段怎么写的" | `recall/` 检索 | 已实现 |
| **算得出** | "报市稿改到第几版了" | `work_ledger` 聚合 | 有实现，未接入对话 |
| **记得住** | "报告要用业务员口吻" | `remember` 工具 + 核心记忆库 | 已接线（2026-08-20），含 forget |
| **到点提醒** | "报市材料周三前交" | **Apple 提醒事项** | 工具已有，缺"提议建提醒" |

**前两条最容易互相冒充。** "第几版"是聚合：召回十个片段模型还得自己数，且容易数错。
**第四条不进记忆库**：`FACT_KINDS` 里没有 `commitment`，`Fact` 上没有 `due_at`——
一旦有了日期字段，这里迟早长成第二个、更差的日历。

本文其余部分只讲第一条（检索），第三、四条见第七节。

## 二、上下文预算：三条通道，互不挪用

```
L0 常驻   每轮无条件付      ≤ 800 token    偏好 + 设置 + 今日日程提醒
L1 召回   模型主动要才付    ≤ 3000 token   recall / recall_expand
L2 旁路   永不进上下文      0 token        ASR 热词、别名归并、检索文本注入
```

- **L0 里一次匹配都没有**：偏好因为数量少所以全带，日程因为有日期所以按日期查。
  "想得起"从来不需要检索。
- **L1 是工具，不是预处理**：每轮自动检索 = 每轮无条件付费，而大多数轮次用不到。
  和技能懒加载同一个道理。
- **L2 最省钱也最容易被忘**：几百个专名喂给 ASR 是投影出去的，一个 token 都不占。

## 三、切片：三层，各管各的事

```
文件 / 会话
  └─ 章节 section        跟标题走，可能上万 token   → 定位"在哪一部分"
       └─ 展示段 passage  ~500t，不重叠              → 命中后返回给模型的就是它
            └─ 匹配窗口 window ~200t，15% 重叠       → 只进索引，从不直接返回
```

**为什么必须分成两层**：窗口切小是为了命中准，展示段切大是为了读得完整。
合成一层就得互相迁就——要么命中糊，要么返回的是半句话。
（V5_dev 的 `RETURN_PARENT_SECTION` 是同一件事：命中子块、返回父段。）

### 参数（对齐 V5_dev 实战值）

| 常量 | 值 | 依据 |
|---|---|---|
| `WINDOW_TARGET_TOKENS` | 200 | 其 `CHUNK_TARGET_UNITS=160`，实测子块中位 223 字符 |
| `WINDOW_OVERLAP_TOKENS` | 30（15%） | 答案跨边界时，无重叠会切成两半、两边都不完整 |
| `WINDOW_MIN_TOKENS` | 70 | 短尾并入前块，不留孤立短句 |
| `WINDOW_MAX_TOKENS` | 300 | 超长句按子句、再按字符细切 |
| `PASSAGE_TARGET_TOKENS` | 500 | 其父段中位 458 字符 |
| `TABLE_TOKENS_PER_WINDOW` | 260 | **按 token 不按行数**：行长差几十倍，按行数必爆块 |

实测我们的窗口：中位 213t，p10=56，p90=310。V5_dev：中位 223 字符，p10=169，p90=301。

### 切分点优先级

空行 > 句末标点 > 冒号 > 单换行 > 逗号（只有超长无标点句才用到最后一档）。
整段不超目标就**不切**——为了切而切只会让每块都读不完整。

### 各类语料的树形

| 语料 | 层级 |
|---|---|
| Word / PDF / Markdown | 文件 → 标题（多级，含中文"一、/（一）/1."）→ 展示段 → 窗口 |
| 表格 | 文件 → 表区 → 行组（**每层继承表头**，一行脱开表头没有意义）|
| 聊天 | 会话 → 轮 → 展示段 → 窗口（**episode 层待建，见第八节**）|

## 四、索引：是投影，不是第二数据源

`recall.sqlite3`，每账户一份（隔离靠路径，和会话存储一致）。随时可删，从原始文件和
会话日志完整重建。

| 表 | 存什么 |
|---|---|
| `recall_sources` | 来源、uri、内容哈希、时间 |
| `recall_nodes` | 节点树（含 `text_hash`、`summary`、`tokens`）|
| `recall_fts` | FTS5 全文（中文 n-gram 展开，unicode61 不切中文）|
| `recall_vectors` | **按 `text_hash` 存，不按节点存** |
| `recall_node_entities` | 知识图谱接缝 |

### 三条省钱的设计

1. **增量到节点**：按 `(id, 内容哈希)` 求差。追加一轮对话只重算新增节点，
   不整份重写——否则一天下来几十次重复 embedding。
2. **向量按内容共享**：同一份材料的 docx/md/pdf 三种渲染、散在多个归档目录里的
   同一个文件，正文一样就共用一条向量。**实测 18.6 万窗口去重后只剩 1.4 万，省 92%。**
3. **来源标识用路径不用文件名**：同名文件遍地都是，用文件名会互相覆盖——
   踩过这个坑，5002 份材料入库只剩 559 份。

### 写入时机

- **词法索引**：本地几毫秒，轮末同步做 + 文件写入即入索引 → 新内容立刻能被找到
- **向量**：走网络，后台补算 → 端点抽风时最坏只是"这段暂时没向量"，不是检索坏了

## 五、检索管线

```
元数据过滤（时间 / 来源类型 / 实体）   ← 结构化条件先于语义，别让向量猜
        ↓
BM25 top20  +  dense top20（bge-m3）
        ↓ RRF 融合（k=60，不依赖分数同尺度）
        ↓ cross-encoder 精排（bge-reranker-v2-m3）
        ↓ 时间衰减做乘子（半衰期 45 天）
        ↓ 内容哈希去重 → top_k = 6
      返回：命中窗口所在的**展示段**
```

**时间维度是我们加的，V5_dev 没有**——手册是静态的不需要，而记忆里"上次""最新一版"
是最高频问法。用连续衰减做乘子而不是再融合一次名次：名次融合在 k=60 下把差异压得太平，
0.3 权重永远翻不动相邻名次；而两条同样相关的证据里，新的那条本来就该赢。

**两个后端都可缺席**：拿不到 embedding 退回纯词法，拿不到 rerank 用融合名次，
**且降级原因写进结果**，不悄悄变差。

## 六、返回什么：展示段 + 标价的展开地图

```json
{
  "id": "…", "text": "……完整的一段正文……", "tokens": 480,
  "path": ["报市稿", "二、几点建议", "1. 建设中试基地"],
  "duplicates": 2,
  "expand": {
    "up1":  {"tokens": 928,  "title": "1. 建设中试基地", "summary": "……"},
    "up2":  {"tokens": 3171, "title": "二、几点建议",     "summary": "……"},
    "file": {"tokens": 5399, "title": "报市稿"}
  },
  "neighbors": {"prev": "…", "next": "…"}
}
```

- **每个展开选项标价**。只有价格没有货物，选择还是盲的——所以还要 `summary`。
- **超上限（6000t）不硬灌**，降级成目录让模型再挑一次。
- **`duplicates`**：折叠掉的重复份数，重复不该占预算。
- **`prev` / `next` 落在展示段这一层**：往后是"这件事后来怎么样"，
  往前是"为什么会有这一段"。兄弟窗口是半句挨半句，回答不了这两个问题。

### 目录与 prev/next 的分工

|  | 目录（标题 + 摘要） | prev / next |
|---|---|---|
| 文档 | 主路径 | 基本用不上 |
| 对话 | 挑"哪件事" | 追"这句之后他答了什么" |

对话的语义是**顺序**的，目录表达不了；文档的语义是**结构**的，顺序意义不大。

## 七、写入侧（记）与提醒

**记忆是一个工具，不是一条流水线。** 模型在对话里、读转录时、看文件时发现值得记的
东西就调 `remember`——它已经把内容读过一遍了，再跑一遍抽取是为同一次阅读付两次钱。

- 没有闸门、没有正则、没有第二次模型调用
- 调和（ADD/UPDATE/NOOP）负责去重：同一件事说十遍，库里还是一条
- 四种 kind：`entity`（正名别名）、`preference`、`setting`、`decision`
- **风险如实记下**：模型可能漏调，兜底只有用户说"记一下"。
  用正则兜底等于把病请回来——宁可漏，不要那张表

**带日期的承诺走 Apple 提醒事项**，不进记忆库：按日期查而不是靠命中、同步到手机、
到点会响、勾掉就等于忘掉。且不得从聊天推断出待办就写入——只能**提议**，用户点一下。

### 上下文压缩的状态口径

- 压缩由三条独立安全线触发：token、待整理会话的序列化体积、历史工具结果累计量。
- 活动记录必须同时保存“压缩前”“实际触发原因”“压缩后”三组信息，不能拿压缩后的数值解释压缩前的触发。
- 未达到 token 安全线但由另外两条安全线触发时，界面必须明确写“token 未超”，不得笼统写成“token 已超过阈值”。
- 压缩只缩小模型工作上下文，原始对话、工具结果和执行轨迹仍留在事件存档中。

### 明确不做

- 不把压缩摘要当记忆来源：它为"断点续作"而造，留的是"还没做完的"，
  丢的恰是"已经定了什么"——而后者才是三个月后要找的。
  但可作为 episode 摘要的输入之一，那是当时模型对"什么重要"的判断，白拿的信号。
- 不给记忆库加日期字段（见第七节）。
- 不用关键词表决定该不该记、该用哪个技能、哪些名字是同一个（见 harness 对比文档）。

## 九、知识图谱接缝

图还没建，但位置留好了，且**默认实现真的接在管线里跑**——返回空集而检索照常工作，
所以接缝天天被执行到，建图那天不会才发现签名不对。

- `recall_node_entities`：节点 ↔ 实体，带 mention 与置信度
- `GraphStore` 协议：`resolve` / `neighbors` / `evidence_nodes`——刻意只有三件事，
  接口小，换实现才不牵动检索
- 检索支持 `entities=[...]`，实体过滤**先于语义**
