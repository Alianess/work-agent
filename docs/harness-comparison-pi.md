# Harness 对比：Pi vs work_agent

> 对比对象：`badlogic/pi-mono`（2026-08 主干，本地已 clone）与本仓库当前实现。
> 所有数字均为源码实测，不引用二手文章。

## 判断标准

harness 是给模型的**控制工程**，职责是让模型更好发挥，不是替它做决定。
提示词应当**必要且最少**：凡是能靠模型自身能力完成的，就不要写进提示词；
凡是靠提示词反复叮嘱才能维持的行为，多半是别处的设计有洞。

---

## 一、每轮固定开销

| 项目 | Pi | work_agent | 倍数 |
|---|---|---|---|
| 系统提示词模板 | **1352 字符**（其中 1022 是"pi 自己的文档在哪"，只在问 pi 本身时有用；真正的行为指令 **330 字符**） | **3625 中文字符** | ≈ 11× |
| 技能索引 | 每技能 3 个 XML 字段（name/description/location） | **4252 字符** JSON（`indent=2`，每技能 6 个字段，含 `mention`/`label`/`enabled` 等模型用不上的字段） | — |
| 模型工具数 | **4**（read / write / edit / bash） | 5 个文件工具 + `update_plan` + `sys_skill` + shell + MCP | — |
| 合计（harness 自撰文本） | ≈ 340 token | ≈ 8000 字符 → 6000+ token | **≈ 20×** |

中文 token 密度高于英文，实际差距比字符比更大。**这笔钱每一次 API 调用都要付一遍**，
而且是从上下文窗口里先切走的一块。

---

## 二、七个问题（按严重程度）

### 1. 用提示词补循环的洞 —— 最严重

`react.py:_default_system_prompt` 里最长的两段，全部在讲同一件事：

> "只输出 assistant content 而不输出 tool_calls，会被运行时立即视为最终答复并结束整个 ReAct……
> 只要你的正文中还会出现'我会''现在开始''下面''接下来''随后'等尚待执行的动作，就不得只输出 content"
>
> "只要用户要求生成、整理、修改或交付文件，而本轮尚未成功执行写入类工具，就绝对不得输出 content-only 最终答复"

**约 1200 字符，占系统提示词三分之一。**

Pi 的 `agent-loop.ts` 全长 796 行，核心循环约 110 行，终止条件就一句：本条消息里没有 toolCall 就停。
**提示词里一个字都没提这件事。**

Pi 靠的是结构而不是叮嘱：

- **steering messages** —— 用户在模型跑的时候打字，消息在下一次 assistant 响应前注入
- **follow-up messages** —— 模型停下来之后，外层循环再问一次"还有排队的消息吗"，有就继续

也就是说：模型提前收尾了，**人补一句就接上**，不需要提示词预先恐吓。
我们没有这两个机制，所以只能靠提示词硬顶——**这 1200 字符是在为缺失的循环设计付租金**。

> 已核实：本仓库 `steering` / `follow_up` / 排队消息机制**一个都没有**，
> `react.py` 里与中途干预相关的只有 13 处 `cancel_check` / `AgentCancelled`——
> 也就是说用户中途只能**打断**，不能**追加**。模型提前收尾了，只能重开一轮。

### 2. 关键词预判路由 —— 替模型做决定

`web_server.py` 里有三个函数在用**子串匹配**猜用户想干什么：

```python
looks_like_meeting_minutes_request()   # "会议"/"纪要" AND ("录音"/"整理"/...)
looks_like_office_request()            # ".docx"/"word"/"表格"/"研报"/...
looks_like_official_document_request() # "红头文件"/"发文字号"/...
```

命中之后，往上下文里塞一条**祈使句**：

> "本轮匹配技能：meeting-minutes。先调用 sys_skill(op='open', skill_id='meeting-minutes') 载入完整流程，再按说明执行。"

这是典型的**限制而非辅助**：

- 用户说"帮我把这个 pdf 里的表格数据算一下" → 命中 `looks_like_office_request` → 被指向 docx/pdf/pptx/xlsx 技能，
  而真正该做的可能是直接 bash + python 读一下
- 模型本来能从技能 description 自己判断，现在被一条硬编码规则抢先定了调
- 这三个函数还是**又三张常量表**，和别名表、热词表同病

Pi 的做法：技能列表照给，附一句 "Use the read tool to load a skill's file **when the task matches its description**"，
**由模型自己匹配**。没有任何预判路由。

### 3. 技能是协议，不是文件

Pi：技能在提示词里只有三行 XML，正文躺在磁盘上，模型**用它本来就有的 read 工具**去读。
没有技能网关、没有 op、没有工具名映射。

work_agent：`sys_skill` 是一个带 `open`/`show`/`call` 三段协议的工具，技能工具经由它分层暴露。

代价是链式的：
协议 → 需要工具名映射 → `SKILL_TOOL_ALIASES` / `COMMON_SKILL_TOOLS` 常量表 → 就是你早先指出的那张表。
**表不是根因，协议才是。** 换成"读文件"，这张表自动消失。

### 4. 工具输出截断了，但没有回头路

work_agent（`shell_tools.py:287`）：stdout 截到 20000 字符，stderr 12000，**丢掉的部分就没了**。

Pi（`tools/truncate.ts`）：2000 行 / 50KB 双限，**超出部分写进临时文件，把路径给模型**，
而且这条规则写在 bash 工具的 description 里，模型知道有这回事——想看哪段自己去 read。

差别不是省了多少 token，是**信息有没有回头路**。
我们跑一次长命令，第 20001 个字符之后的东西模型永远看不到，也不知道自己没看到。

### 5. 技能索引每轮 4252 字符常驻

15 个技能，`indent=2` 的 JSON，每个技能 6 个字段。其中 `mention`、`label`、`enabled`
是给前端用的，模型拿来做路由用不上。

同样是"给模型看的目录"，Pi 的格式只有 name/description/location 三项。

### 6. ~~审批要多花一次模型调用~~ —— 不改，保留

`approval_review.py` 每次需审批的 shell 命令会再调一次模型独立审查。

**这条不照抄 Pi。** Pi 是单任务、跑完即散、用户全程盯着终端；我们是长期运行、有真实副作用、
用户经常不在跟前。风险模型不同，多一次 500 token 的轻量审查是划算的。

### 7. 风格约束分两类，只能删一类

系统提示词段 4"展示规则"（216 字）讲的是**智能体怎么跟用户说话**——不要逐条播报、
不要输出思维链、最终答复不要重复过程。这类**对话风格**每轮都在付钱，可以删。

**但产出物风格必须留。** 周报的动词开头句式、纪要的格式、公文的文种与要素——
这些决定材料像不像国企办公场景里该交的东西。它们已经在 skill 里（`work-reports`、
`official-document`、`biweekly-style.md`），按需加载，位置本来就对。

> Pi 的跑分（Terminal-Bench 一类）只测任务完成度，**不测"像不像那么回事"**。
> 一份材料读起来像咨询公司写的，跑分不扣一分，拿去报市就是废稿。
> 这块价值 Pi 的设计里没有对应物，照抄等于把我们唯一的差异化扔掉。

## 三、我们做对的地方

不要全盘照抄，以下几点 Pi 没有或更弱：

1. **请求装配是日志的纯函数**（`build_request_messages`）。Pi 的 context 是可变对象在循环里传递。
   我们这边"模型收到的东西不可能来自没被记录的状态"，这条是我们更强。
2. **late system blocks 放在最新用户消息之前**——变动内容靠后，前缀稳定，
   对 prompt cache 友好。这个位置是对的。
3. **压缩用 shadow 而非删除**（`compaction/replacement` 事件遮蔽而不销毁），
   人看的 transcript 和模型看的 messages 是两个投影。Pi 的 compaction 更接近直接替换。
4. **记忆/注意力层**。Pi 是无状态 coding agent，做完即散，它不需要这些。我们需要。

## 四、真正的动作：归位，不是删减

把系统提示词逐段归类后，结论变了——**大部分内容不是该删，是放错了地方。**

| 段 | 字数 | 内容 | 应该在哪 |
|---|---|---|---|
| 1、2 | 669 | ReAct 终止语义 | **循环结构**，不是提示词文字 |
| 4 | 216 | 展示规则（对话风格） | 删 |
| 5 | 309 | update_plan 用法 | `update_plan` 的 tool description |
| 6 | 496 | 终端权限 + `shell_exec` 是 argv 不是 shell | `shell_exec` 的 description |
| 7 | 434 | `.venv` 环境约定 | **项目上下文文件**（对应 Pi 的 contextFiles） |
| 8 | 686 | 何时用哪个文件工具 | 各文件工具的 description |
| 9 | 374 | 待办只指 Apple 提醒事项 | **apple-schedule skill**，按需加载 |
| 10 | 361 | 技能分层协议 | 技能改成读文件后自动消失 |

归位的好处不只是省 token：**每条规则离它约束的东西更近**。
讲 `shell_exec` 的话写在 `shell_exec` 的 description 里，模型看到该工具时才付这笔钱，
也不会一边读 `read_text_file` 一边看着 shell 的规矩。

搬完之后系统提示词剩约 200 字。

### 执行顺序

按"收益 ÷ 风险"排，前四步互相独立：

1. **规则归位**：段 5/6/8 → tool descriptions；段 7 → 项目上下文文件；段 9 → apple-schedule skill
2. **删掉三个 `looks_like_*` 预判路由**，技能选择交还模型
3. **技能索引瘦身**：6 字段砍到 3
4. **工具输出落盘 + 给路径**，让截断有回头路
5. **删段 4** 对话风格约束（产出物风格不动，它在 skill 里）
6. **修循环**：加 steering / follow-up 队列，**然后**才删段 1、2 的终止语义。顺序不能反
7. **技能从协议改成文件**，顺带干掉 `SKILL_TOOL_ALIASES`

不做：审批二次模型调用保留（见 §二.6）。

前六步做完，每轮固定开销大致从 6000+ token 降到 1500 以内，
降的全是**限制模型的那部分**，产出物质量相关的东西一条没动。
