## 一、第一性原则：这是个什么东西

**它是替一个具体的人持有工作全貌的常驻助理。**

不是编码智能体，不是问答机器人，不是工作流引擎。三条推论直接决定架构，
且每一条 Pi 这类 coding agent 都没有对应物：

### 1. 它跨时间存在 → 记忆是本体，不是插件

coding agent 的生命周期是一个任务：启动、干完、散场，下次从零开始。
我们的生命周期是**一个人的职业时间线**。同一个人名会在三个月里出现在录音、
文件、聊天和日程里，它必须知道那是同一个人。

**所以记忆不能是挂在旁边的一个模块，它必须是会话日志的投影。**

### 2. 它自己启动 → 主动性是本体

coding agent 的循环由用户回车启动，没有输入就没有它。
我们的助理必须能在没人说话的时候开口："报市材料周三到期了""这份录音你还没处理"。

**所以循环必须能被时间和外部事件触发，不只是被用户消息触发。**

### 3. 它的产出要给别人看 → 产出物质量是本体

Terminal-Bench 只测任务完成度。一份材料读起来像咨询公司写的，跑分一分不扣，
拿去报市就是废稿。

**所以文种、口吻、格式的知识是核心资产，不是可裁剪的装饰。**
它们归属 skill（按需加载），不归属 harness 提示词（每轮付费）。

## 二、三个面 + 一个投递层

```text
┌─────────────┬─────────────┬─────────────┐
│  单个聊天    │    项目      │   Friday    │   ← 界面（attach 上来的观察者）
│  一次性任务  │  长期、绑定  │  唯一持续    │
│  结果可回流  │  project_id │  对话入口    │
└──────┬──────┴──────┬──────┴──────┬──────┘
       └─────────────┼─────────────┘
                     │
            ┌────────▼────────┐
            │   会话内核        │   ← 服务端常驻，不属于任何窗口
            │  事件日志 · 循环   │
            │  记忆 · 工具       │
            └────────┬────────┘
                     │
       ┌─────────────┼─────────────┐
       ▼             ▼             ▼
    微信推送      桌面提醒      前端小红点      ← 投递通道
```

**界面是观察者，不是宿主。** 会话在服务端活着，谁 attach 谁看得见，
全部断开它照样跑。这不是抽象洁癖——**Friday 在没人看着的时候到底算不算在跑，
现在的架构里没有答案**（HTTP 端点直接绑死在 React 前端上）。有了 attach/detach 才有答案：
跑，只是没人连着，消息堆在那里等投递。

## 三、提醒 = 主动消息的投递回执

这是产品上最容易做错的一处，单独说清楚。

**错误做法**：把"Friday 主动说话"和"提醒用户"做成两个功能，各写各的内容。
结果是两份措辞不一致的东西，用户还得对照着看。

**正确模型**：一份内容，两个投影。

```text
Friday 想说话
     │
     ├──► ProactiveMessage 落在 Friday 会话里    ← 内容的唯一副本
     │       未读 = 这条消息的属性
     │
     └──► Notification 是它的摘要投影            ← "Friday 有 1 条未读：XXX"
             作用：把用户从"新聊天"拉回 Friday
             投递通道：微信 / 桌面 / 小红点
```

规则：

- 内容只有一份，存在会话里
- **未读是消息的属性**，不是通知的属性
- 用户点开 Friday → 消息标记已读 → 通知自动消失
- 微信、桌面提醒、小红点是**同一件事的三条投递通道**，不是三个功能
- 通知投递失败不影响消息存在；消息已读则未投递的通知作废

### 一个必要的类型区分

这条主动消息**不一定要进模型上下文**——它是给人看的。
所以会话时间线上的消息，必须分成两类：

| | 进模型 | 进人看的时间线 |
|---|---|---|
| 用户消息 / 助手回复 / 工具结果 | ✅ | ✅ |
| **通知类消息**（投递回执、状态提示、系统事件） | ❌ | ✅ |

**我们已经有这个形状**：`derive_messages()`（模型视图）与 `derive_transcript()`（人的视图）
本来就是同一条日志的两个投影。缺的只是把"通知类消息"这个事件类型定出来。
**这是补一个类型，不是改架构。**

## 四、Harness：骨架 + 钩子

从 Pi 学的四条，每条对应我们一个具体的洞。

### 1. 会话服务端化，客户端可插拔

Pi 的 `LiveSession` 持有 `connections: Set<Connection>`，支持 attach / detach / broadcast。

对应我们：三个界面 + 微信通道复用同一个内核，界面不再是宿主。
这也是 [TODO Phase 8](../TODO.md)（消息通道适配器）能成立的前提——
没有这一层，每接一个通道就要复制一遍运行逻辑。

### 2. AgentMessage 是 LLM Message 的超集

调模型前经 `convertToLlm` 过滤掉 UI-only 消息。见上一节。

### 3. 循环是骨架 + 钩子，不是巨石

Pi 的循环本体约 110 行，可变部分全是钩子：

| 钩子 | 用途 | 我们的对应物 | 现状 |
|---|---|---|---|
| `beforeToolCall` → `{block:true}` | 拦下工具调用 | **审批**（保留，见下） | 焊死在 react.py |
| `afterToolCall` | 改写工具结果 | 输出截断、落盘 | 分散各处 |
| `transformContext` | 调模型前改上下文 | 压缩、**记忆注入** | 压缩焊死；记忆没接口 |
| `shouldStopAfterTurn` | 优雅停 | 步数上限 | 焊死 |
| `getSteeringMessages` | 跑的时候插话 | — | **没有** |
| `getFollowUpMessages` | 停了之后追问 | — | **没有** |

我们的 `react.py` 是 2965 行巨石。

**审批不砍，改成钩子。** 逻辑一行不改，但循环立刻瘦下来，
而且[记忆层](memory-layer-design.md)的"常驻层注入"将来就是再挂一个 `transformContext`。

### 4. steering / follow-up 是队列，不是打断

现在用户中途**只能打断，不能追加**（`react.py` 里只有 13 处 cancel 相关，没有任何排队机制）。
所以模型提前收尾时只能重开一轮，我们只好在系统提示词里花 669 字反复恐吓它别提前收尾。

**先补队列，再删那 669 字。顺序不能反。**

## 五、明确不学 Pi 的

| 我们的 | Pi | 为什么不学 |
|---|---|---|
| 审批二次模型调用 | 沙箱即权限 | Pi 单任务、用户全程盯着终端；我们长期运行、有副作用、人常不在跟前。风险模型不同 |
| 产出物风格知识 | 无 | 跑分不测"像不像那么回事"，但这是我们的全部价值 |
| 长期记忆、人物关系图 | 无 | 见第一性原则 1 |
| 主动性、日程、Apple 待办 | 完全被动 | 见第一性原则 2 |
| 项目作为一等公民 | 只有 cwd | 见 TODO Phase 1–2 |
| 事件日志唯一真相 + 压缩用遮蔽 | 更弱 | 这条我们本来就更强，别退回去 |

**一句话：学它的骨架，不学它的边界。**

## 六、分层

```text
第 8 层  投递：微信 / 桌面提醒 / 小红点          ← 同一条消息的三个出口
第 7 层  主动推进：到期、风险、承诺、会议前后
第 6 层  自动回忆 Context Hydration              ← 预算受控
第 5 层  混合检索与图增强检索
第 4 层  长期记忆：抽取 → 候选 → 确认 → 失效
第 3 层  材料与证据：原文、出处、时间线、权限
第 2 层  关系与情报中心：实体、关系、项目扩展对象
第 1 层  ProjectManagementPort + PlaneAdapter
第 0 层  Plane 项目执行基座
────────────────────────────────────────────
第 -1 层 Harness：会话内核 · 事件日志 · 循环钩子   ← 本文新增，所有层的地基
```

原有 TODO 的 0–8 层不变。**新增的是下面那层**——之前它是隐含的，
所以循环、审批、压缩、记忆全焊在一起，上面每一层都得绕开它做。

而且 B 和 C 都要挂在它的钩子上——A 不做完，B 的记忆注入和 C 的通道适配都没有挂载点。

## 八、红线

沿用 TODO 原有七条，并新增四条：

1. **界面不得成为会话的宿主。** 任何"关掉窗口这个会话就没了"的实现都是错的。
2. **主动消息与提醒不得各存一份内容。** 通知永远是消息的投影。
3. **产出物风格知识不得上移进 harness 提示词。** 它属于 skill，按需加载。
4. **harness 不得靠提示词维持行为。** 凡是要靠反复叮嘱才成立的规矩，
   说明结构有洞——去修结构，不要加字。
